```
GET /rest/v1/tools?select=id,pickup_location   →  42501 permission denied for table tools
```

## 1. Reported bugs (map, layout, PWA)

### ~~BUG-1~~ ✅ FIXED — Map pins drift when zooming — **High**

**Corrected diagnosis — third attempt.** This one took three passes, and the
first two diagnoses were wrong. Recording all three, because the elimination is
the useful part:

1. **`body { zoom: 1.08 }`** — a real defect, but not this one. Removing it did
   not stop the drift.
2. **The 16px fan-out** — also a real defect, and it did move pins with zoom,
   but only pins that shared a coordinate. Fixing it did not stop the drift
   either. The tell was the user's report that the pins *"stay the same distance
   apart but just shift"* — a fan-out bug changes the spacing, so a symptom with
   **unchanged spacing and a uniform shift** had to be something applied
   equally to every marker.
3. **`el.style.position = "relative"` on the marker root** — the actual cause.

**Actual cause.** mapbox-gl positions markers with a stylesheet rule:

```css
.mapboxgl-marker { position: absolute; top: 0; left: 0; will-change: transform }
```

`pinElement()` set `position: relative` as an **inline** style, and inline beats
a stylesheet. Every marker therefore fell out of absolute positioning and back
into normal flow inside `.mapboxgl-canvas-container`, picking up its static flow
offset *in addition to* mapbox's `translate()`. That is a constant screen-space
offset — and a constant screen offset is a varying ground offset, so the whole
marker layer slid across the basemap as the zoom changed while keeping its
internal spacing.

The `position: relative` was there to give the absolutely-positioned name label
a containing block. `pinElement` now moves that job to an inner wrapper and
leaves the marker root's `position` alone — which also removes the dependency on
mapbox's CSS having loaded at all. It lives in `src/lib/mapPins.js` now, so it
is testable: `never sets an inline position on the marker root` fails if anyone
reintroduces it (verified by reintroducing it).

**Second, independent cause (also fixed):** the co-located-pin fan-out was a
constant
**16-pixel** `Marker#offset`. A fixed pixel offset is a *varying* geographic
offset, because metres-per-pixel changes with every zoom level. At the live
data's latitude:

| zoom | 16 px on the ground |
|---|---|
| 10 | 1 915 m |
| 13 | 239 m |
| 16 | 30 m |
| 18 | 7.5 m |

So any pin in a cluster of two or more slid ~1.9 km across the basemap between
zoom 10 and zoom 18. And the live data guarantees a cluster: `CreateGroup.jsx`
copies the creator's chest coordinate onto the new group (LOGIC-8), so the group
`Rock'n Tool Chest` and the chest `Jim B.` have byte-identical `approx_lat/lng`.
Both were offset; the unrelated solitary chest pin, in a cluster of one with
offset `[0, 0]`, stayed put — which is why the drift looked selective.

This one only affected pins sharing a coordinate, which the live data
guarantees. **Fix:** `fanOutDelta()` in `src/lib/mapPins.js` now returns a lat/lng delta
instead of a pixel offset, applied to the marker's own coordinate. Every pin is
now fixed to a real location at every zoom; co-located pins simply overlap again
when you zoom far enough out, which is the honest behaviour. The angle comes
from a hash of the entity id, so it is stable across reloads and independent of
query order — a fixed display offset, not a re-jitter of the stored point (which
`CLAUDE.md` forbids). 30 m is far inside the ~800 m jitter the pin already
carries, so it discloses nothing. Ten tests in `src/lib/mapPins.test.js` pin
this down, including an explicit guard that the return value is not a pixel
tuple.

**Also fixed, and genuinely broken — just not the cause of the drift:**

- **`body { zoom: 1.08 }`.** mapbox-gl projects with `container.clientWidth`
  (layout px) but reads the pointer with `getBoundingClientRect()` (visual px,
  8% larger under `zoom`). Scroll-zoom is cursor-anchored, so each zoom step
  re-centred the *whole map* ~8% off — a subtle drag on the map as a whole, not
  the dramatic per-pin slide. `zoom` also broke `100vh` (BUG-3). Replaced with
  `html { font-size: 108% }` plus all 85 arbitrary `px` values converted to
  `rem`, which reproduces the scale exactly and respects the user's own browser
  font-size setting.
- **No `map.resize()`.** Mapbox measures its container once, at construction.
  The container is no longer a fixed `60vh`, so a `ResizeObserver` now calls
  `map.resize()` — without it the canvas keeps a stale size after a rotation or
  a mobile toolbar collapse, and the projection drifts out of alignment.

**Lesson for the next map bug:** "pins move when zooming, panning is fine" means
something is expressed in *screen pixels* that should be expressed in
*coordinates*. Then use the spacing to tell the two classes apart — if the pins'
spacing changes, it is per-pin (`Marker#offset`, fan-out); if the spacing holds
and the whole layer shifts, it is applied to every marker equally (marker
positioning, container sizing, a transform on an ancestor). Check the computed
`position` of `.mapboxgl-marker` in devtools first: it must be `absolute`.

### ~~BUG-2~~ ✅ FIXED — White stripe between the map and the bottom nav — **Medium**

**Cause:** the map is hard-coded to `h-[60vh]` (`src/pages/Search.jsx:169`), while its page wrapper is `min-h-screen bg-page pb-24` (`src/components/PublicLayout.jsx:9`). Everything from 60vh down to the fixed nav is page background (`#ECEAE4`) showing through.

**Note on the fix, second attempt.** The first attempt used `min-h-full` on the
Search root and `flex-1` on the map. That made the map *shorter*, not taller: a
percentage height inside a flex item does not reliably resolve, because the
item's own height is only definite after layout, so `min-height: 100%`
collapsed to the content height. The working version is a pure flex chain with
no percentages — the shell's content row is `flex flex-col`, the screen fills it
with `grow`, and the map layer is `absolute inset-0` inside a `relative` flex
child, which is the one construction whose height always resolves. `.app-content
> * { flex-shrink: 0 }` stops a screen taller than the row being squashed
instead of scrolling.

**Fix:** make the map fill the space that is actually left. Replace the fixed 60vh with a flex column, or compute it:

```jsx
{/* header is ~132px, bottom nav ~84px incl. safe area */}
<div className="w-full" style={{ height: "calc(100dvh - var(--toolber-header) - var(--toolber-nav))" }}>
```

Use `100dvh`, not `100vh` — see BUG-3. Also drop `pb-24` from the wrapper when the map view is active, or the padding re-creates the gap.

### ~~BUG-3~~ ✅ FIXED — PWA does not fit the screen; wrong icon — **High**

Three separate defects:

1. **The icons do not exist.** `vite.config.js:26-27` declares `icon-192.png` and `icon-512.png` in the manifest, but `public/` contains only `favicon.svg`. The install prompt and home-screen icon therefore fall back to a screenshot/letter glyph. Export `src/components/ToolberIcon.jsx` (the mascot mark) to `public/icon-192.png`, `public/icon-512.png`, plus a `maskable` 512 variant and an `apple-touch-icon-180.png`, and add `<link rel="apple-touch-icon" href="/apple-touch-icon-180.png">` to `index.html`.
2. **No viewport-fit / safe areas.** `index.html:6` is `width=device-width, initial-scale=1.0` with no `viewport-fit=cover`, and `BottomNav.jsx:61` uses a fixed `pb-3.5`. In standalone mode on a notched device the nav sits under the home indicator. Add `viewport-fit=cover` and `padding-bottom: calc(0.875rem + env(safe-area-inset-bottom))`.

## 2. Database security & RLS

### ~~PRIV-1~~ ✅ FIXED — Any user can make themselves a platform admin — **Critical**

`0001_init.sql:278`:

```sql
create policy profiles_update_own on profiles for update to authenticated using (auth.uid() = id);
```

The policy restricts *which row* can be updated. Nothing restricts *which columns*. `SELECT` was revoked and re-granted per column (line 356), but `UPDATE` still carries Supabase's default table-wide grant. So:

```sql
UPDATE profiles SET is_platform_admin = true WHERE id = auth.uid();
```

succeeds for any signed-in user — and `is_platform_admin` is the sole gate on reading the entire `events` analytics stream and every user's `feedback` (lines 326, 332).

**Fix — mirror the SELECT treatment:**

```sql
revoke update on profiles from authenticated;
grant update (
  display_name, avatar_url, home_lat, home_lng, approx_lat, approx_lng,
  pin_radius_meters, pin_placement_mode, map_pin_hidden, profile_complete,
  tos_accepted_at, tos_version, auto_approve_vetted_borrowers, theme_preference
) on profiles to authenticated;
```

`is_platform_admin` and `has_payment_method_on_file` are deliberately excluded — both are server-owned. Assertion already written: `supabase/tests/borrow_and_group_rls_test.sql` (currently inside the `todo_start` block).

### ~~PRIV-2~~ ✅ FIXED — Self-granted "vetted" status can auto-reveal pickup locations — **Critical**

Same root cause as PRIV-1, different payload. `request_borrow()` (`0001_init.sql:419-432`) treats a borrower as vetted if they share an approved group with the lender **or** `has_payment_method_on_file` is true. If the lender has `auto_approve_vetted_borrowers` on, the request is approved with no human in the loop, `pickup_location_revealed_at` is stamped, and `get_pickup_location()` starts returning the address.

An attacker sets their own `has_payment_method_on_file = true` (PRIV-1) and harvests the pickup address of every tool whose owner opted into auto-approval — the exact outcome the whole column-grant design exists to prevent.

**Not exploitable today** only because no UI sets `auto_approve_vetted_borrowers`, so it is `false` for everyone. That is a UI accident, not a control.

**Fix:** PRIV-1's column grant. Additionally, since the payments clause is dormant pre-launch (per `CLAUDE.md`), consider dropping the `has_payment_method_on_file` branch from `request_borrow()` entirely until payments actually ship.

### ~~DOS-1~~ ✅ FIXED — Anyone can mark anyone's tool as broken — **Critical**

`report_malfunction()` (`0001_init.sql:512-535`) is `SECURITY DEFINER` and performs **no authorization check whatsoever**. Any signed-in user can call it with any tool id and immediately flip that tool to `unavailable_malfunction`, removing it from circulation. Only the owner can undo it (`resolve_malfunction`), and only after noticing.

Tool ids are readable by every visitor (search is public), so this is a one-liner that takes the entire catalogue offline:

```js
for (const t of allTools) await supabase.rpc("report_malfunction", { p_tool_id: t.id, p_note: "x" })
```

**Fix:** require a relationship. A reporter should have at least one `borrow_requests` row for the tool with status `approved` or `completed`, or be the owner:

```sql
if v_owner_id is null then raise exception 'Tool not found'; end if;
if v_owner_id != auth.uid() and not exists (
     select 1 from borrow_requests
     where tool_id = p_tool_id and borrower_id = auth.uid()
       and status in ('approved','completed')
   ) then
  raise exception 'Only the owner or a past borrower can report this tool';
end if;
```

Consider also making the report a *flag for owner review* rather than an immediate status change, and rate-limiting reports per user.

### SEC-1 — The notify trigger will embed a service-role key in readable SQL — **High**

`0001_init.sql:645-658`:

```sql
headers := jsonb_build_object(..., 'Authorization', 'Bearer YOUR_SERVICE_ROLE_OR_ANON_KEY'),
```

Function bodies live in `pg_proc.prosrc`, which is readable by any role including `authenticated`. Pasting a service-role key here hands full database access to every logged-in user. This is a placeholder today — the danger is at the moment someone fills it in.

**Fix:** store the key in Supabase Vault and read it at call time, and use the **anon** key with a separate shared secret rather than the service-role key:

```sql
select decrypted_secret into v_key from vault.decrypted_secrets where name = 'notify_fn_token';
```

Also: this function is the only `SECURITY DEFINER` function in the schema **missing `set search_path = public`** (compare lines 53, 233, 373). A `SECURITY DEFINER` function without a pinned `search_path` can be hijacked by a caller-controlled schema. Add it.

### ~~SEC-2~~ ✅ FIXED — Every invite code in the app is world-readable — **High**

Confirmed live, with no session at all:

```
GET /rest/v1/groups?select=* →
[{"name":"Rock'n Tool Chest", "invite_code":"XHGVFT2", "default_exchange_location":"Jim's trailer", …}]
```

`0006_anon_search_read_access.sql:42` adds `groups_select_anon ... using (true)` with no column-level grant (the migration's own comment argues `invite_code` is "meant to be discoverable/non-secret by design"). The result is that the invite code confers no access control at all — anyone on the internet can enumerate every group's code, and `default_exchange_location` (a real-world physical meeting spot) is public too.

If that is genuinely intended, the "invite code" naming is misleading and should be dropped in favour of a plain group id. If it is not intended:

```sql
revoke select on groups from anon, authenticated;
grant select (id, name, neighborhood_label, city, zip_code, admin_id, approx_lat, approx_lng, created_at)
  on groups to anon, authenticated;
-- invite_code and default_exchange_location reachable only via an RPC that
-- checks approved membership
```

Note that `join_group()` takes the code as its only argument, so today the code is both the credential and public knowledge. Also note `GroupDetail.jsx:47` does `select("*")`, which pulls `invite_code` into the browser for non-members even though the UI hides it (`:197`) — the data is in the network tab regardless.

### ~~SEC-3~~ ✅ FIXED — `join_group()` is an unauthenticated invite-code oracle and a notification spam vector — **Medium**

Two problems in `0001_init.sql:584-610`:

1. **Callable by `anon`.** Postgres grants `EXECUTE` to `PUBLIC` by default. Confirmed live: an anon call returns `23502 null value in column "profile_id"` — including the internal row contents in the error detail — while an invalid code returns `Invalid invite code`. The two distinct errors make it a free code-validity oracle, and the error detail leaks a generated membership uuid and the group id.
2. **Notifies on every call.** The `insert ... on conflict do nothing` is idempotent, but the notification insert below it is not. A user can call `join_group` in a loop and flood the group admin's inbox (and, once the Edge Function is live, their email). It also re-notifies for a membership that was already **denied**, so a rejected user can pester an admin indefinitely.

**Fix:** `revoke execute on function join_group(text), request_borrow(uuid, boolean), report_malfunction(uuid, text), … from anon, public;` then `grant execute … to authenticated;` for the whole RPC surface, and only insert the notification when the membership row was actually created:

```sql
if v_membership_id is null then return null; end if;  -- already pending/approved/denied
```

### SEC-4 — The notify Edge Function trusts any caller — **Medium**

`supabase/functions/notify/index.ts` takes `{ notification_id }` from an unauthenticated-ish request (the platform only requires a valid apikey, and the anon key is public) and sends an email using the service role. Anyone who can guess or observe a notification uuid can replay the send. There is no idempotency key, no rate limit, and no check that the caller is the database trigger.

**Fix:** add a shared secret header set from Vault by the trigger and verified in the function; record a `sent_at` on the notification row and return early if already set.

### SEC-5 — Unmapped notification types email users who opted out — **Low**

`index.ts:63` — if a type isn't in `TYPE_TO_PREFERENCE`, the function logs a warning and **sends anyway**. Fail closed instead. Separately, `group_join_requested/approved/denied` are all mapped to `borrower_reminders`, which is semantically wrong — a user who turns off borrower reminders silently stops getting group decisions.

### RLS-1 — A group admin can forge membership for an arbitrary user — **Medium**

`memberships_admin_update` (`0001_init.sql:292`) has a `USING` clause and no `WITH CHECK`, so Postgres reuses `USING` as the check. That constrains the *group*, not the *member*: an admin can `UPDATE group_memberships SET profile_id = '<any user>' WHERE …` inside their own group, manufacturing an approved membership for someone who never asked. Since approved co-membership is what makes a borrower "vetted" (PRIV-2), this matters.

**Fix:** add `with check (profile_id = group_memberships.profile_id)` — or better, drop the direct UPDATE policy entirely and route every decision through `decide_group_membership()`, which already checks admin rights.

### RLS-2 — No way to leave a group or cancel a request — **Medium**

- `group_memberships` has no `DELETE` policy for the member, so a user cannot leave a group. Combined with PRIV-2, membership is a permanent trust grant.
- `borrow_requests` has no `UPDATE` policy at all and no cancel RPC, so the `cancelled` enum value is unreachable and a borrower cannot withdraw a request.

### RLS-3 — `events` cannot be logged by logged-out visitors — **Low**

`events_insert_own` is `to authenticated with check (profile_id = auth.uid())`, and `0006` gave `anon` read access but no insert path. Search is public, so the entire anonymous funnel — the top of the acquisition funnel — is invisible to the internal analytics that `CLAUDE.md` describes as "the entire analytics strategy".

### RLS-4 — Missing index on `group_memberships.profile_id` — **Low**

`Groups.jsx:31` filters by `profile_id`, but the only index is the `unique (group_id, profile_id)` constraint, whose leading column is `group_id`. Add `create index group_memberships_profile_idx on group_memberships (profile_id);`.

## 3. Borrow-flow logic

### ~~LOGIC-1~~ ✅ FIXED — An approved request reveals the pickup location forever — **High**

Nothing ever moves a `borrow_requests` row to `completed`, and nothing ever moves a tool back from `borrowed` to `available` after a real return. `get_pickup_location()` only checks `status = 'approved'`, with no time bound. One approved borrow in 2026 still returns the owner's address in 2030.

This is the single biggest gap between the schema and the stated privacy model. It needs a return/complete flow: a `complete_borrow_request(p_request_id)` RPC callable by either party that sets `status = 'completed'` and the tool back to `available`, plus (recommended) an expiry on the reveal — e.g. `and (decided_at > now() - interval '30 days')` in `get_pickup_location()`.

### ~~LOGIC-2~~ ✅ FIXED — `request_borrow()` does not check tool status or existing requests — **High**

`0001_init.sql:394` validates only that the tool exists and isn't yours. It does not check that the tool is `available`, and it does not check for an existing pending request from the same borrower. So a borrower can:

- request a tool that is already borrowed, malfunctioning, or unavailable (the UI blocks this at `ToolDetail.jsx:210`, but the RPC is directly callable);
- fire N pending requests for the same tool, each generating a notification.

Worse, the unconditional `update tools set status = 'requested'` at line 445 will drag a `borrowed` or `unavailable_malfunction` tool back to `requested`, corrupting the owner's view.

**Fix:** guard on `status = 'available'`, and `on conflict`-style dedupe on `(tool_id, borrower_id) where status = 'pending'` (a partial unique index expresses this cleanly).

### ~~LOGIC-3~~ ✅ FIXED — Denying one request frees a tool another borrower is holding — **High**

`deny_borrow_request()` (`0001_init.sql:504`) unconditionally sets the tool to `available`. With two pending requests on one tool — entirely possible given LOGIC-2 — approving A then denying B marks the tool available while A still has it, and A's `approved` row keeps revealing the address. The same unconditional-write bug exists in `resolve_malfunction()` (line 556), which sets `available` even if the tool was `borrowed` when it was flagged.

**Fix:** recompute status from the request set rather than assigning it blindly:

```sql
update tools set status = case
  when exists (select 1 from borrow_requests where tool_id = v_tool_id and status = 'approved') then 'borrowed'
  when exists (select 1 from borrow_requests where tool_id = v_tool_id and status = 'pending')  then 'requested'
  else 'available' end
where id = v_tool_id;
```

### ~~LOGIC-4~~ ✅ FIXED — `approve_borrow_request()` does not check the current status — **Medium**

It will happily approve a request that is already `denied`, `cancelled`, or `completed`, re-revealing the pickup location for a borrow that was explicitly refused. Add `if v_status != 'pending' then raise exception …`.

Also note that `if v_lender_id != auth.uid()` (line 470) evaluates to `NULL` — not `true` — when the request id does not exist, so the guard falls through and the function proceeds against a non-existent row. Use `is distinct from`, and check `not found` first. The same pattern appears in `deny_borrow_request` (499), `resolve_malfunction` (551) and `set_borrower_supervision` (572).

### LOGIC-5 — `join_group()` returns NULL on a repeat join, and the client treats that as success — **Medium**

`returning id into v_membership_id` yields NULL when `on conflict do nothing` fires. `Groups.jsx:105` and `GroupDetail.jsx:95` only check `error`, so a duplicate join renders "Request sent." to a user whose request was in fact ignored (or was already denied). Return a status enum, and have the UI reflect it.

### LOGIC-6 — `CreateGroup` performs two writes with no transaction — **Medium**

`CreateGroup.jsx:29-71` inserts the group, then inserts the creator's membership. If the second fails, the group exists with zero members and the creator is not in it — the exact state migration 0005 was written to fix. The UI reports it (which the tests cover), but the orphan remains and the invite code is burned.

**Fix:** a single `create_group(...)` RPC doing both inserts in one transaction. This also fixes CQ-1.

### ~~LOGIC-7~~ ✅ FIXED — Invite codes use `Math.random()` — **Medium**

`src/lib/inviteCode.js:9`. `Math.random()` is not cryptographically secure, and V8's xorshift128+ state is recoverable from a modest number of outputs. Given SEC-2 makes codes public anyway the practical impact is nil *today*, but if invite codes are ever made secret this is a pre-broken foundation. Use `crypto.getRandomValues`, and generate the code server-side inside the `create_group` RPC (LOGIC-6) rather than in the browser with a client-side retry loop.

### LOGIC-8 — Group pins are placed exactly on the admin's chest pin — **Medium**

`CreateGroup.jsx:39-40` copies `profile.approx_lat/lng` onto the group. `CLAUDE.md` warns specifically about per-group pin placement, and this is a variant of that hazard: a group pin sitting on *exactly* the same coordinate as a chest pin identifies which chest belongs to the group admin. `ToolMap.jsx:123-140` visually fans co-located pins apart, which hides the collision from the eye but not from the API response.

**Fix:** derive the group pin from the centroid of its approved members' `approx` points (with a minimum member count before showing a pin at all), or let the admin place it manually. Never copy a chest coordinate verbatim.

## 4. Frontend correctness

### ~~FE-1~~ ✅ FIXED — Search results can be overwritten by a stale response — **High**

`Search.jsx:69-95` debounces by 250 ms but never cancels the in-flight request. Type "saw", pause, type "sander": if the first query is slower, its results land last and the user sees results for a query they have moved on from — with no visible clue.

**Fix:** track a request id (or `AbortController`) and drop responses that are not the latest:

```jsx
const seq = useRef(0);
const runSearch = useCallback(async (q) => {
  const mine = ++seq.current;
  const { data, error } = await request;
  if (mine !== seq.current) return;   // superseded
  …
}, []);
```

### ~~FE-2~~ ✅ FIXED — Every map marker is destroyed and rebuilt on every keystroke — **High**

`Search.jsx:42` constructs the `focus` object inline during render:

```jsx
const focus = focusType && focusId ? { type: focusType, id: focusId } : null;
```

That is a new object identity on every render. It is a dependency of `ToolMap`'s marker effect (`ToolMap.jsx:185`), so the effect re-runs on every render of `Search` — including every keystroke in the search box. Each run removes and re-creates every `mapboxgl.Marker`, and when a focus target is set it re-fires `flyTo` and **toggles the popup**, so the popup flickers open/closed as the user types.

**Fix:** memoise it — `const focus = useMemo(() => (focusType && focusId ? { type: focusType, id: focusId } : null), [focusType, focusId]);` — and split `ToolMap`'s effect so that `focus` handling is separate from marker construction.

### ~~FE-3~~ ✅ FIXED — Every protected screen crashes if mounted without a resolved session — **Medium**

`ToolDetail.jsx:58`, `MyTools.jsx:48`, `Favorites.jsx:52`, `Groups.jsx:43`, `GroupDetail.jsx:85`, `ListTool.jsx:42`, `CreateGroup.jsx:38`, `Onboarding.jsx:78` all dereference `user.id` with no guard. They are safe *only* because `RequireAuth` renders a spinner until `loading` is false. Any future route that forgets that wrapper — or a `Suspense`/lazy boundary that changes mount ordering — is an instant white screen.

This is not theoretical: the test suite had to add an explicit gate (`test/setup.jsx` → `renderPage`) to mount these screens at all. Add `const { user } = useAuth(); if (!user) return null;` at the top of each, or make `useAuth()` throw a typed error that an error boundary catches.

### ~~FE-4~~ ✅ FIXED — No error boundary and no 404 route — **Medium**

`App.jsx` defines no `path="*"` route, so any unknown URL renders an empty page with a bottom nav. And there is no `ErrorBoundary` anywhere, so any render-time exception blanks the whole app with no recovery. Add both.

### ~~FE-5~~ ✅ FIXED — `AuthContext` can hang on "loading" forever — **Medium**

`AuthContext.jsx:32-40`: if `supabase.auth.getSession()` *rejects* (offline, bad URL, CORS), nothing sets `loading = false` and `RequireAuth` shows its spinner indefinitely. Add `.catch(() => setLoading(false))`.

Two related issues in the same effect:
- the `onAuthStateChange` callback (line 42) does not check the `mounted` flag that the `getSession` path does, so it can set state after unmount;
- it performs an `await`-ing Supabase call (`loadProfile`) directly inside the callback. supabase-js holds an internal auth lock across that callback; issuing another client call from inside it is a documented deadlock risk. Defer with `setTimeout(() => loadProfile(id), 0)`.

### ~~FE-6~~ ✅ FIXED — `supabaseClient.js` warns but then throws anyway — **Medium**

`src/lib/supabaseClient.js:6-13` logs a friendly `console.warn` about missing env vars and then calls `createClient(undefined, undefined)`, which throws `supabaseUrl is required` — a blank screen with the helpful message buried in the console. Either throw a clear error with the same text, or render a config-error screen.

### ~~FE-7~~ ✅ FIXED — Errors are silently swallowed in six handlers — **Medium**

`MyTools.jsx:132` (`decide`), `Favorites.jsx:58` (`removeFavorite`), `GroupDetail.jsx:109` (`decide`), `GroupDetail.jsx:119` (`saveLocation`), `Groups.jsx:37`/`94` (both loads), `Search.jsx:104` (groups load) all follow `if (!error)` with no `else`. A denied approval, a failed save, or an RLS rejection produces a button that appears to do nothing. Surface every one of them.

### ~~FE-8~~ ✅ FIXED — Public Search links straight into a login wall — **Medium**

Migration 0006 and `PublicLayout` went to real effort to make Search work logged-out, but `/tool/:id` sits inside `RequireAuth` (`App.jsx:33`). A logged-out visitor can browse results and then hits a redirect on the first tap. Either make Tool Detail public in a reduced form (no request button, no favourite, pickup locked — which it already is), or label results so the sign-in requirement is not a surprise.

### ~~FE-9~~ ✅ FIXED — `select` pulls the full `search_vector` on every result — **Low**

`Search.jsx:19` includes `search_vector` in the column list. That is the full lexeme vector for name + description + category, for up to 60 rows, on every keystroke, and it is never used in the UI. Drop it.

### ~~FE-10~~ ✅ FIXED — Unbounded queries — **Low**

`Groups.jsx:91` fetches **every** group with **every** membership row nested, with no limit or pagination; `GroupDetail.jsx:74` uses `.in("chest_id", approvedIds)` with an unbounded id list (URL-length limits apply around a few hundred members); `MyTools`, `Favorites` and the borrow-request lists have no limit either. Search is capped at 60 with no "load more".

### ~~FE-11~~ ✅ FIXED — Internal mockup filenames leak into the UI — **Low**

`Settings.jsx:28-30` renders "see toolber-settings.html, toolber-notifications.html, and toolber-privacy-location.html for the design" to the end user. Replace with user-facing copy.

### ~~FE-12~~ ✅ FIXED — `ToolMap` is untestable and fails opaquely — **Low**

`ToolMap.jsx:6` reads `import.meta.env.VITE_MAPBOX_TOKEN` at module scope, which means the module cannot be imported in any non-Vite environment (Node, tests, SSR). It is the one source file excluded from the AVA suite for this reason. Move the token read inside the component, and export `escapeHtml`/`pinElement` so they can be tested.

### ~~DEP-1~~ ✅ FIXED — `react-router-dom` has two moderate advisories — **Medium**

`npm audit`: open-redirect via backslash in `<Link>`/`useNavigate` (GHSA-wrjc-x8rr-h8h6) and arbitrary constructor injection in SSR hydration (GHSA-337j-9hxr-rhxg), both affecting `6.0.0 – 7.17.0`. ### ~~DEP-2~~ ✅ FIXED — The map defeats its own lazy-loading — **Medium**

`Search.jsx:9` lazy-loads `ToolMap` specifically so that "it's only fetched by people who actually switch to Map view". But `vite.config.js:14` raises `workbox.maximumFileSizeToCacheInBytes` to 4 MB precisely so the mapbox chunk gets **precached by the service worker** — which downloads it for every visitor on first load, in the background, regardless of whether they open the map. }

```sql
-- PRIV-1: which columns can `authenticated` write to on profiles?
-- An empty result means the table-wide default grant is still in force.
select grantee, privilege_type, column_name
from information_schema.column_privileges
where table_name = 'profiles' and grantee in ('anon','authenticated')
order by grantee, privilege_type, column_name;

-- Table-level grants (the coarse picture)
select grantee, table_name, string_agg(privilege_type, ', ' order by privilege_type)
from information_schema.role_table_grants
where table_schema = 'public' and grantee in ('anon','authenticated')
group by grantee, table_name order by table_name, grantee;

-- SEC-3: who can execute the RPCs?
select p.proname,
       array(select unnest(p.proacl)::text) as acl,
       p.prosecdef as security_definer,
       p.proconfig as config          -- null here means no `set search_path` (SEC-1)
from pg_proc p join pg_namespace n on n.oid = p.pronamespace
where n.nspname = 'public' order by p.proname;

-- Every RLS policy, and whether it has a WITH CHECK (RLS-1)
select tablename, policyname, cmd, roles, qual, with_check
from pg_policies where schemaname = 'public' order by tablename, policyname;

-- Any table with RLS off is a hole
select tablename, rowsecurity from pg_tables
where schemaname = 'public' order by rowsecurity, tablename;

-- LOGIC-1: approved requests that will reveal an address forever
select count(*) from borrow_requests
where status = 'approved' and decided_at < now() - interval '30 days';

-- LOGIC-3: tools whose status disagrees with their request set
select t.id, t.name, t.status,
       count(*) filter (where br.status = 'approved') as approved,
       count(*) filter (where br.status = 'pending')  as pending
from tools t left join borrow_requests br on br.tool_id = t.id
group by t.id, t.name, t.status
having (count(*) filter (where br.status = 'approved') > 0 and t.status <> 'borrowed')
    or (count(*) filter (where br.status = 'approved') = 0 and t.status = 'borrowed');
```

## Appendix B — What the new test suite does and does not cover

`npm run test:all` runs seven gates: the pickup-location guard, biome lint, tsc, knip, semgrep, npm audit, and 222 AVA tests. All pass on the current tree, with zero lint warnings.

**Covered:** every page and component's data flow against a stubbed Supabase client — including explicit assertions that no query ever names `pickup_location`, that `get_pickup_location` is only called on an approved request, that borrow/approve/deny/join go through RPCs rather than direct writes, that the onboarding jitter never stores the raw position as the public pin, and that each action logs its `events` row.

**Not covered by AVA, by construction:** everything in §2 and §3. Those live in Postgres, and a mocked client cannot reach them. That is what `supabase/tests/*.sql` is for — `supabase test db` (needs Docker + `supabase start`).

**Not yet run:** the two pgTAP suites were written during this audit but could not be executed here — Docker is not installed on this machine, so `supabase test db` cannot start a local stack. They are expected to pass except for the three assertions deliberately wrapped in `todo_start`/`todo_end` (PRIV-1, PRIV-2, DOS-1), which encode the intended behaviour and will start passing as those findings are fixed. **Run them before trusting them.**

**Also not covered:** the `notify` Edge Function (Deno; needs its own test harness), any real browser rendering, and visual/layout regressions — which is why BUG-1 through BUG-3 were found by hand rather than by the suite. `ToolMap.jsx` itself still can't be imported outside Vite (mapbox-gl and `import.meta.env` at module scope), but its logic now lives in `src/lib/mapPins.js` and is covered by 16 tests.
